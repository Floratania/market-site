# Де база даних

Saleor зберігає свій каталог, канали, ціни та замовлення в PostgreSQL. У локальному проєкті служба бази визначена в `saleor-platform/docker-compose.yml`, сервіс `db`.

Після запуску з `docker compose -p vsmarket-local ...` дані зберігатимуться у Docker volume `vsmarket-local_saleor-db`. Це окрема локальна база; робоча SQL Server база VS Market не переносилася й не змінювалася.

Локальні адреси після запуску:

- Сайт: http://127.0.0.1:8790/
- Saleor GraphQL: http://127.0.0.1:8000/graphql/
- Saleor Dashboard: http://127.0.0.1:9000/
- PostgreSQL: `127.0.0.1:5432`, локальна база `saleor`.
- pgAdmin: http://127.0.0.1:5050/ (локальний контейнер Docker).

## pgAdmin

Додано pgAdmin 4 9.18 у той самий Docker-проєкт `vsmarket-local`. Сторінка входу повертає HTTP 200; підключення з контейнера pgAdmin до `saleor` перевірено через SELECT: у схемі public 148 таблиць. Для запуску: `node start-pgadmin.mjs`; основний `start-saleor.mjs` також запускає pgAdmin. Налаштування зберігаються у volume `vsmarket-local_saleor-pgadmin`, база Saleor — у попередньому `vsmarket-local_saleor-db`.

Логін і випадково згенерований пароль pgAdmin збережені тільки локально у `pgadmin.local.json`, виключеному з Git. Дані серверного входу — у `.env.pgadmin`; файл пароля PostgreSQL — `.pgpass.saleor.local`, також виключені з Git. Це окремий логін pgAdmin, не користувач Dashboard Saleor.

У pgAdmin попередньо додано сервер «Saleor — локальна база», група VS Market. Підключення з контейнера: host `db`, port `5432`, database `saleor`, user `saleor`. Автоматичний пароль підключення завантажується через PGPASS_FILE. Для окремого Windows-клієнта PostgreSQL host буде `127.0.0.1`. У дереві pgAdmin: Servers → VS Market → Saleor — локальна база → Databases → saleor → Schemas → public → Tables.

## MSSQL і PostgreSQL

Saleor 3.23 використовує PostgreSQL: у встановленому коді є SearchVectorField, GinIndex, django.contrib.postgres та pg_advisory_xact_lock. Перехід на SQL Server не є заміною рядка підключення: потребує переробки моделей, запитів, міграцій і блокувань та підтримки власної версії Saleor.

Рекомендована схема для цього проєкту: робоча 1С/VS Market залишається на SQL Server `vsql\vstm`; адаптер читає потрібні товари й залишки; Saleor використовує свою PostgreSQL. SQL-підключення вже перевірено, постійна синхронізація ще не активована.

08.10.2026: після уточнення «як краще» для подальшої розробки обрано цю схему. Базу Saleor на MSSQL не переключено. Перевірка встановленого образу показала залежності не лише в налаштуваннях, а й у моделях, міграціях, пошуку, масивних полях та транзакційних блокуваннях. Окремий fork Saleor потребував би перенесення цих механізмів і подальшого супроводу.

## Повні views номенклатури для MSSQL

Підготовлено `integration/nomenclature-full-views.sql` і пояснення `integration/nomenclature-full-views.md`: 5 нових views для номенклатури, характеристик і їхніх табличних частин. Усі 123 реквізити експорту конфігурації зіставлено з раніше перевіреними фізичними колонками. Оригінальні views не змінюються; дані 1С також не змінюються. SQL поки не застосовано на сервері.

Для перевірки SELECT без створення views: `node integration/verify-full-views.mjs`. Під час останньої спроби поля user і password в `integration/bi-connection.local.json` були порожні; тому компіляцію SELECT на сервері ще не підтверджено. Паролі потрібно вводити лише у локальному файлі.

Джерела: [встановлення Saleor](https://docs.saleor.io/setup/docker-compose), [моделі Saleor 3.23](https://github.com/saleor/saleor/blob/3.23/saleor/product/models.py), [контейнер pgAdmin](https://www.pgadmin.org/docs/pgadmin4/latest/container_deployment.html).

Макет `?demo=1` використовує явно позначені ілюстративні товари, щоб дизайн можна було переглядати незалежно від наповнення бази.
