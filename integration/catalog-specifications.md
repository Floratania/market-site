# Контракт характеристик 1С → Saleor → сайт

Статус 08.10.2026: характеристики та фото імпортовано до локального Saleor;
109 моделей містять 453 окремі варіанти/SKU. Повторний ручний імпорт реалізовано;
періодична синхронізація не налаштована.

18 дозволених властивостей визначено в `product-enrichment.mjs`. Вони записані
як штатні атрибути Saleor на варіантах та як `public_specs` для вітрини.
Користувач підтвердив одиниці ширини/висоти — міліметри; атрибути NUMERIC мають
unit `MM`. Неоднозначні/службові значення не публікуються. 22 суперечливі розміри
між основним полем та додатковою властивістю винесено в
`product-dimension-conflicts.csv`; одна незаповнена модель також пропущена.

Фото знайдені через номенклатуру присоединённых файлов і том зберігання 1С.
Файли читаються з `\\\\vsql\\Share_1c\\BAS_WST_OknaBas\\`, перевіряються розмір,
формат і SHA-256; завантажені оригінали прив'язуються до конкретного SKU.
558 джерельних записів дали 548 різних зображень у межах товарів після
усунення повторів; фото є для 412 SKU. 43 товари не мають доступних фотографій
у поточному джерелі. Вітрина показує заповнювач для таких варіантів.

Фото в картках і на сторінці товару показуються повністю (`object-fit: contain`)
з відступами. `product-media.css` підключено після основного стилю вітрини.
Галерея показує всі зображення саме обраного SKU; натискання мініатюри перемикає
основне фото. У картках каталогу та на сторінці товару є кнопки попереднього й
наступного фото, якщо обраний SKU має кілька зображень; лічильник показує номер
поточного фото. Перегортання не підмінює фото іншого кольору або SKU. Збільшення
з картки відкриває саме показане фото. З картки або сторінки товару можна відкрити перегляд у `<dialog>`:
перемикання фото кнопками/стрілками клавіатури, масштаб 100–400%, кнопка
«Повністю», подвійний клік та закриття Escape. Початковий масштаб вміщує весь
оригінал у вікні; файли 1С не обрізаються і не редагуються.
`product-photo-verification.json` звіряє кількість різних фото кожного
опублікованого SKU з джерельним маніфестом і перевіряє URL двох фото.
У поточному каталозі 18 SKU мають більше одного фото, з них 3 — рівно два.

На сторінці моделі ширина і висота вибираються окремими полями, далі — сторона
відкривання та колір (якщо вони є у джерелі). Значення з різним регістром і
зайвими пробілами об'єднуються в один пункт; одиниці вимірювання зберігаються.
Наступні списки залежать від попередніх: висота від ширини, відкривання від
розмірів. Список кольорів завжди містить усі кольори моделі. Вибір кольору
зберігає поточні розміри й відкривання, якщо така комплектація існує; інакше
обирається існуючий SKU цього кольору і повідомляються змінені параметри.
Показуються тільки існуючі комбінації.
При зміні попереднього параметра інші зберігаються, якщо відповідний SKU існує;
інакше повідомлення пояснює, які параметри доступного варіанта змінилися.
Якщо однакові параметри відповідають кільком SKU з іншою комплектацією,
додатковий список показує лише ці SKU. Великого списку всіх варіантів моделі немає.

Каталог показує окрему картку для кожного кольору моделі. Регістр і зайві
пробіли не створюють дублікати кольорів. Пошук розпізнає `900×2050`, `900*2050`,
`900x2050`, `900 х 2050`, `900 2050`, а також підписані ширину/висоту; розміри
порівнюються з підтвердженими атрибутами, не вгадуються з назви. Після пошуку
за розмірами або фільтрації розмірів комплектації з різними цінами показуються
окремими картками. Ціна відповідає знайденим комплектаціям, без дешевших
розмірів тієї ж моделі. Без фільтра розмірів «від» показується лише за наявності
кількох різних цін усередині картки цього кольору. Відкриття картки передає
конкретний variant ID, але сторінка моделі зберігає весь набір кольорів і SKU.
`verify-catalog-colors.mjs` перевіряє цей контракт на поточному API каталогу.

Фільтр «Наявність на складі» має варіанти «Усі товари», «Є на будь-якому складі»,
«Мамаївці» та «Магала». Для вибраного складу залишаються лише SKU з позитивним
`stock.quantity`; це вже доступний залишок, резерви повторно не віднімаються.
Фільтрація виконується до групування за моделлю/кольором і обчислення ціни.
Показується дата джерельного знімка. За відсутності перевіреного складського
каналу або датованого знімка фільтр не вигадує наявність із Saleor total.
Вибір записується в URL (`warehouse`) та передається на сторінку моделі для
перегляду самовивозу. Зміна категорії зберігає склад; «Скинути» очищує його.
`verify-warehouse-filter.mjs` звіряє фактично показані SKU зі складськими рядками API.

`catalog-fields.md` / `catalog-fields.json` містять усі реквізити двох довідників з локального XML. `schema-discovery.sql` виконано: джерела виявилися views із неповним набором реквізитів. Живі результати — `live-source-analysis.md`; ідентифікатори розшифрованих властивостей — `public-property-map.json`.

## Передача публічних значень

Імпортер має розшифрувати посилання, нормалізувати одиниці після підтвердження, сформувати Saleor product/variant та записати дозволені публічні параметри в metadata. Службові поля і повний сирий рядок не передаються браузеру. Прямі ключі: `material`, `opening`, `color`, `profile`, `product_type`, `manufacturer`, `country`, `width`, `height`, `length`, `weight`, `unit`, `warranty`. Для одиниці параметра — окремий ключ `width_unit`, `height_unit` тощо. Значення — рядки для відображення. Нульові порожні значення 1С потрібно відрізнити від реальних до публікації.

Додаткові властивості і довільні дозволені реквізити передаються через `public_specs` — JSON у metadata:

```json
[{"key":"glass_package","label":"Склопакет","value":"Двокамерний","filterable":true}]
```

Це приклад контракту, не декодоване значення з робочої бази. Ідентифікатор key стабільний і латинський; label — назва для покупця; value — розшифроване значення; unit — необов'язкова перевірена одиниця; filterable — явний дозвіл фільтра. Решта полів JSON не проходить у відповідь API. `public_specs` має формувати імпортер лише з дозволеного переліку властивостей.

Спершу застосовуються параметри товару, потім заповнені параметри варіанта з тим самим key. Порожній параметр варіанта не скидає параметр товару. Не змішувати характеристики різних варіантів. Назви для покупця мають бути однаковими для одного key у всьому каталозі.

Сайт показує всі передані specifications у блоці «Характеристики», а filterable — у фільтрах. Розміри з різними одиницями не зливаються в один варіант фільтра. Пошук враховує значення параметрів. HTML у значеннях відображається як текст.

## Перевірка повноти живих views

Користувач уточнив SQL Server: `vsql\vstm`, SQL-автентифікація. Параметри вводяться локально в `bi-connection.local.json` (виключено з Git), а `inspect-bi.mjs` використовує SQL-клієнт mssql. Запуск із директорії storefront:

```powershell
node integration/inspect-bi.mjs
```

Результати зберігаються у `bi-schema.local.json`; логіни й паролі туди не записуються. Для named instance потрібна доступність SQL Browser; якщо він вимкнений, додайте в локальний JSON перевірений числовий port. Encrypt увімкнено; помилку сертифіката слід розв'язувати відповідно до налаштувань вашого сервера. Сам скрипт не надає логіну read-only права — використовуйте обліковий запис лише для читання.

1. Результати schema-discovery.sql уже отримано через SQL. Для повторної перевірки запустити inspect-bi.mjs.
2. liveViewColumn і liveSourceColumns у catalog-fields.json заповнено за живою структурою. Простого SELECT із поточних views недостатньо для відсутніх реквізитів.
3. Перевірити додаткові реквізити номенклатури **і характеристики**, довідник значень та план властивостей; виключити множення товарних рядків після JOIN.
4. Для відсутніх потрібних полів підготувати зміну експорту або окремий read-only канал до джерела 1С. Самовільно BI-views не змінювати.
5. Звірити декілька реальних дверей/вікон із картками 1С, включно з характеристикою, одиницями та залишком обох складів, і лише після цього увімкнути імпорт.
