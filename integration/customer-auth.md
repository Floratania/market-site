# Облікові записи покупців VS Market

Додано 08.10.2026. Облікові записи створюються в локальному Saleor / PostgreSQL; у frontend немає окремої бази паролів.

## Сторінки

- `/account/login` — вхід.
- `/account/register` — реєстрація імені, прізвища, email і пароля.
- `/account` — кабінет, зміна імені та прізвища, вихід.
- `/account/confirm` — підтвердження email за одноразовим посиланням.
- `/account/forgot` і `/account/reset` — відновлення пароля.

У шапці головної та товарних сторінок з’явилося «Увійти». Після входу — «Мій кабінет». Повернення до каталогу зберігає деморежим і попередню адресу. Профіль не містить вигаданої історії замовлень: заявки менеджеру поки не підключені.

## Підключення та сесія

`integration/customer-auth.mjs` викликає штатні мутації Saleor accountRegister, tokenCreate, tokenRefresh, confirmAccount, requestPasswordReset, setPassword, accountUpdate та query me.

JWT, refresh token і csrf token Saleor зберігаються лише на сервері. Браузер отримує випадковий ідентифікатор сесії в cookie `vs_market_session`, HttpOnly, SameSite=Lax. Cookie Secure вмикається для HTTPS `STOREFRONT_PUBLIC_URL`. Зміни приймаються лише від точної налаштованої origin і лише як JSON. Реєстрація та зміна профілю передають тільки явно дозволені поля; користувач не може передати isStaff, permissions, metadata або чужий customerId.

Є обмеження частоти запитів, терміну сесії, розміру полів і кількості сесій. Відновлення пароля не розкриває, чи існує адреса. Затримку Saleor після невдалої спроби входу показано як HTTP 429.

Локальна сесія живе до 24 годин у пам’яті одного процесу вітрини; після перезапуску потрібен повторний вхід. Для кількох процесів на виробничому сервері необхідне спільне сховище сесій. Також потрібно налаштувати передавання справжньої адреси клієнта від довіреного reverse proxy для обмеження спроб входу.

## Улюблені та порівняння

Списки зберігаються в PostgreSQL Saleor у власному `User.metadata["vsmarket:selections:v1"]`. Вітрина використовує токен покупця та штатну мутацію `updateMetadata`; права адміністратора для цього не потрібні. Сервер бере ID власника з авторизованої сесії. ID з запиту використовується тільки для відхилення застарілої вкладки іншого акаунта.

`GET /api/auth/selections` читає списки, `POST` приймає обмежений набір операцій add/remove/merge. Операції для одного покупця виконуються послідовно й читають свіжі дані, щоб паралельні пристрої не перезаписували весь список. Повторні запити мають ідентифікатори; зберігаються останні 100 для уникнення повторного виконання. Ліміти: 250 улюблених, 4 комплектації в порівнянні. Перевищення показується покупцю.

Гостьові списки переносяться після входу. При реєстрації без підтвердження пошти виконується автоматичний вхід і перенесення; з підтвердженням — після першого входу. Локальні незавершені операції зберігаються окремо для кожного акаунта й вкладки та повторюються після відновлення зв’язку. Вихід не переносить приватні списки в гостьовий список. Синхронізація активної сторінки — кожні 30 секунд, після змін, повернення фокуса та відновлення з’єднання.

Це синхронізація улюблених та порівняння; кошик поки зберігається локально. Дані списків переживають перезапуск вітрини, хоча після перезапуску потрібно увійти повторно. Для кількох процесів вітрини необхідні спільні сесії та блокування записів на рівні БД замість поточної черги одного процесу.

Перевірено автоматизованими тестами двох пристроїв, повторних запитів, втрати з’єднання, виходу, зміни акаунта й захисту чужих ID. `node integration/verify-account-selections.mjs` перевіряє два реальні входи, видалення та запис у PostgreSQL через тимчасового локального покупця, якого прибирає після перевірки.

## Доставка листів

Штатний User emails plugin був активний лише в default-channel. Для vs-market-ua створено окреме налаштування, скопійоване зі стандартного каналу, з доставкою до `mailpit:1025` і його шаблонами. Інші канали не змінені.

Листи підтвердження та відновлення відкривати в **http://127.0.0.1:8025/**. Вони не надходять на зовнішню пошту. Перед запуском для покупців потрібне реальне SMTP-підключення в поштовому плагіні каналу.

`STOREFRONT_PUBLIC_URL` задає точну адресу вітрини для перевірки origin та посилань у листах. Якщо змінюється порт або домен — змінити це налаштування та дозволені клієнтські хости Saleor. Для Linux-сервера потрібна HTTPS-адреса магазину.

## Перевірено

- 8 автоматизованих тестів: сесії, cookie, refresh, whitelist полів, захист origin, ліміти, відновлення; попередні каталог, сторінки товарів і заявки також проходять.
- Живий локальний Saleor: створено тимчасового покупця, підтверджено email через Mailpit, перевірено вхід, профіль, відновлення пароля, відмову старого пароля, вхід із новим паролем та вихід.
- Після перевірки видалено лише створеного тимчасового покупця й його тестові листи.
- HTTP 200 для всіх сторінок кабінету та ресурсів. Візуальна перевірка у браузері не виконана.

Команди з папки storefront:

```text
node --test tests/customer-auth.test.mjs
node check-customer-auth-live.mjs
```

Live-перевірка створює окремий тимчасовий акаунт і запускає ізольовану вітрину на порту 18794. Вона перевіряє, що поштове підключення локальне, перш ніж виконувати реєстрацію.
